## Dagens mål: 

Målet i dag er å lage en forbindelse som senere skal brukes som access-port for Windows i VLAN 20.

### Forventet resultat

## Fremgangsmåte

I går la jeg till ett til nettverkort og i SWITCH-OVS maskinen og koblet det til det interne nettverket CLIENTS-ACCESS. Idag startet jeg opp maskinen og sjekket om det nye nettverkortet har blitt lagt til og hvilke navn det hadde fått. Det heter enp0s9 og dette kortet skal senere brukes som access-forbindelse for Windows, slik at Windows kan kobles til VLAN 20 uten å håndtere VLAN-tagging selv.

Kortet er nå klart til å bli lagt til som port i Open vSwitch. Dette nettverkskortet er koblet til VirtualBox-nettverket CLIENTS-ACCESS og skal senere brukes for klienttrafikk i VLAN 20.

Jeg konfigurerte nettverkskortet enp0s8 som trunk-port i Open vSwitch. Trunk-porten tillater VLAN 10, 20 og 30, slik at trafikk fra disse VLAN-ene kan transporteres mellom pfSense og den virtuelle switchen. Deretter la jeg nettverkskortet enp0s9 til i bridgen br0 og konfigurerte det som en access-port for VLAN 20.

Etter at Open vSwitch var konfigurert med trunk- og access-port, testet jeg forbindelsen fra Windows-klienten til VLAN 20. Målet var at Windows skulle få en IP-adresse fra DHCP-serveren på pfSense i nettverket 192.168.30.0/24.

Ved første test fikk Windows en automatisk APIPA-adresse (169.254.x.x) i stedet for en vanlig IP. Dette betyr at DHCP-serveren ikke svarte. Standard gateway manglet også, så klienten hadde ikke kontakt med pfSense.

Jeg gjennomførte derfor feilsøking av hele forbindelsen, fra Windows-klienten til pfSense.

### 1. Nettverkskonfigurasjon i windows.  
Først kontrollerte jeg nettverkskonfigurasjonen i Windows med: ipconfig  
Og fikk opp:  
IPv4 Address:    169.254.51.73
Subnet Mask:     255.255.0.0
Default Gateway: Tomt  

Dette viste at Windows ikke hadde mottatt en DHCP-adresse fra VLAN 20.  
Jeg testet deretter DHCP-fornyelse med: ipconfig /renew

Men denne kommandoen brukte veldig lang tid på å tilbake svar, engang ventet jeg lenge nok til jeg fikk  feilmeldingen:  
<img width="919" height="90" alt="image" src="https://github.com/user-attachments/assets/2b7245b6-ba6e-4218-954e-779e7e1a0121" />

Ganske tydelig feilmelding, Windows maksinen får ikke kontakt med DHCP-serveren.

### 2. Kontroll av nettverksadaptere i VirtualBox.  
Jeg fikk gjennom konfigurasjonen for adapterne i VirutalBox for SWITCH-OVS og for pfSense og alle nettverksadapterne var koblet til riktig. 

MAC-adressen til pfSense sitt em0 ble sammenlignet med MAC-adressen i VirtualBox. Dette bekreftet at em0 faktisk var nettverkskortet som var koblet til VLAN-LAB.

### 3. Kontroll av VLAN konfig i pfSense grensesnittet.  

I pfSense kontrollerte jeg VLAN-oppsettet under Interfaces → VLANs.

| Beskrivelse       | Parent-interface | VLAN-tag |
|-------------------|------------------|----------|
| SERVERS VLAN 10   | `em0`            | `10`     |
| CLIENTS VLAN 20   | `em0`            | `20`     |

Jeg sjekket også at CLIENTS brukte VLAN 20 på em0, med IP-adressen 192.168.30.1/24.

Med kommandoen ifconfig em0.20 bekreftet jeg at VLAN 20 var aktivt, brukte riktig parent-interface og hadde riktig IP-adresse. Dette viste at VLAN-oppsettet i pfSense var riktig.

### 4. Kontroll av DHCP på pfSense

Jeg sjekket DHCP-innstillingene for CLIENTS. DHCP-området var satt til 192.168.30.100 – 192.168.30.200.

Gateway og interface var også kontrollert. Det var derfor ingen tydelige feil som jeg kunne se i DHCP-oppsettet.
 
### 5. Kontroll av Open vSwitch

Deretter kontrollerte jeg Open vSwitch på SWITCH-OVS.

Bridgen br0 var opprettet, og nettverkskortene var lagt til som porter.

* enp0s8 var konfigurert som trunk og tillot VLAN 10, 20 og 30.
* enp0s9 var konfigurert som access-port for VLAN 20.

Dette betyr at Windows-trafikken på enp0s9 automatisk ble behandlet som VLAN 20, uten at Windows måtte legge på VLAN-taggen selv.

### 6. Tcpdump

For å finne ut hvor trafikken stoppet, brukte jeg tcpdump.  

Jeg lyttet først på VLAN 20-interfacet i pfSense og testet DHCP fra Windows med ipconfig /renew. Det kom ingen pakker frem. 
Jeg testet også parent-interfacet em0, men heller ikke der ble det registrert trafikk.

### 7. Kontroll av status på nettverkskortene i SWITCH-OVS

Til slutt sjekket jeg statusen på nettverkskortene med: ip -br link

Det viste seg at nettverkskortene og bridgen br0 ikke var aktive som forventet.   
* enp0s8 – trunk-port mot pfSense    
* enp0s9 – access-port mot Windows  
* br0 - bridge for nettverkstrafikken  

**Jeg aktiverte dem med:**
sudo ip link set enp0s8 up  
sudo ip link set enp0s9 up  
sudo ip link set br0 up  

Begge kortene var nå oppe, men br0 står som UNKNOWN. *Dette er ikke nødvendigvis en feil for en Open vSwitch-bridge, siden Linux ikke alltid viser en vanlig fysisk link-status for et internt OVS-interface.*

### 8. Endelig test

Etter at nettverkskortene var aktivert, kjørte jeg DHCP-fornyelse på Windows på nytt: ipconfig /renew

**Denne gangen fikk Windows:**

* IP-adresse: 192.168.30.100  
* Nettmaske: 255.255.255.0  
* Standard gateway: 192.168.30.1  

Dette bekreftet at VLAN 20 fungerte.

Feilen skyldtes ikke feil VLAN-ID, feil parent-interface, feil DHCP-område eller feil IP-konfigurasjon i pfSense.

Den konkrete årsaken var at enp0s8 og enp0s9 ikke var aktive. Etter at begge kortene ble satt til UP, fikk Windows DHCP-adresse fra VLAN 20. 
En port kan være riktig konfigurert i Open vSwitch, men trafikken vil likevel ikke fungere dersom selve nettverkskortet ikke er aktivt.
